# 酷澎首次取單：申請結果不明後查詢原單

`store-agent/shipping_core.py` 的 `Workbench._process` 在出貨申請逾時、非成功回覆或缺少正式單號時，保留 `uncertain` 防重送紀錄，接續 `reconcile_cp`。不再要求操作員離開核對視窗再到已處理清單取單。

- 僅透過正式單包裹 ordersheets GET 查詢；20 秒查詢預算、最多 6 次，間隔最多 2 秒。每次 connect/read timeout 依剩餘預算縮短，最多各 3 秒；超過期限回來的結果不接受。
- 比對包裹、訂單識別、收件人、電話、地址、商品及物流公司；只允許出貨狀態和物流號碼向前更新。
- 平台確認可下載且有正式物流號碼才進入原本 `downloadInvoices` 路徑。成功回覆原有 `ready` 結果，前端同一次操作接續 `loadDocument`，顯示共用核對視窗，不自動列印。
- 取消、待取消、商品／收件資料／物流異動立即停止。期限內無法確認時保留鎖；重新操作也只能查詢，不能再申請。重開程式不會清除鎖。
- 已確認單號後若文件下載失敗，保留 `download-failed` 及原單號，不退回出貨申請。
- 新增事件記錄查詢開始、成功、異動、期限用盡及例外種類，不儲存原始平台回應或例外訊息。

不修改 MOMO、列印程式或設定、蝦皮助手、備貨確認的防重送規則。未改動共用前端正式程式；新增前端回歸案例驗證成功回覆後會顯示原單號及共用視窗。

## 驗證

在 `store-agent` 內使用主機既有 Python 環境執行：

```text
python -m unittest discover -p "test_shipping*.py"
```

在專案根目錄執行：

```text
node --test store-agent/test_shipping*.cjs
```

新增 `test_shipping_reconcile.py` 覆蓋申請逾時、備貨後申請逾時、延遲就緒、查詢逾時、失敗回覆、查詢截止、重開後防重送、取消、資料異動、不同包裹及文件下載失敗。全部平台呼叫使用 mock。

主機驗證使用店主指定的既有單，僅允許正式單筆查詢及 `downloadInvoices`，封鎖其他平台端點、備貨與新申請入口；在獨立驗證資料夾下載，避免改變正式處理及列印紀錄。核對主機 HTTP 服務提供的原單與新下載原單頁數、文字一致。真實新出貨逾時情境僅以模擬驗證，不擅自建立新出貨。

舊版主機紀錄只能證實發出申請後沒有成功事件，稍後才下載文件。它沒有保存例外類別，因此不能追溯判定是網路逾時或未辨識的申請回覆；新版事件供下次判讀。

## Wing 已安排出貨的分類

最新正式訂單狀態為 `DEPARTURE`、有物流號碼且沒有取消／待取消異常時，即使沒有本地處理紀錄，也在「已處理」顯示「已安排出貨」，並保留「取回原貨運單」入口。這是快照顯示的分類，不會新增取單、列印或出貨操作紀錄，也不會假設已下載文件。

已有本地處理紀錄時，仍沿用原有規則：保留已取單、已印單、列印次數及人工移回未處理的結果；本地紀錄與最新訂單內容不一致時，仍要求重新核對。同步失敗、沒有物流號碼及取消異常不會套用新的自動分類。MOMO、蝦皮及其他酷澎狀態的規則不變。

`test_shipping_external_arrangement.py` 與同名 `.cjs` 覆蓋同步、重開、遠端資料、清單分類、原單入口、無副作用、異常資料及既有紀錄優先順序。真實單驗證只查詢 ordersheet、包貨快照及下載前核對，不呼叫申請、取單處理或列印接口。
